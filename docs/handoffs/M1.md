## Task

Build the first local interactive Next.js prototype for the Edison school helpdesk. Use App Router and TypeScript, a supported stable dependency set, one lockfile, and clean reusable components. Preserve all planning/continuity files. Record the worker and task in PROJECT_STATUS.md before editing. No hosted accounts or credentials are needed for this milestone.

## Product and design

Create a restrained, modern application: neutral surfaces, one accent color, readable typography, efficient table rows, clear status/priority badges with text, good spacing, keyboard navigation, and usable phone layouts. Avoid decorative gradients, oversized marketing cards, emoji-heavy headings, and empty future-feature navigation.

Build these views with invented fixture data:

1. Login and set-password screen designs. Do not collect/store actual passwords. An explicitly labeled demo user switcher may allow reviewing admin and different technician perspectives. It must be isolated from future production authentication.
2. Open Queue, My Tickets, Collaborating, and permission-filtered Resolved history. Admin also has All Tickets and Administration.
3. Admin intake: requester, location, title/issue, submission date defaulting to today's school-local date with backdating, Walk-in/Email/Phone Call, priority, and optional owner defaulting to Open Queue.
4. Technician intake: Walk-in only, owner fixed to the current technician, selectable collaborators. No creation into Open Queue or another owner's queue.
5. Ticket details: requester/location, one or more optional device observations (type/model/OS/serial/asset tag), primary owner, collaborators, authored work notes, solution, and activity history.
6. Working demo actions: create, claim, add collaborator, add note, change priority, log optional minutes, resolve with a nonblank solution, and admin reassign/reopen. Preserve primary owner when a collaborator resolves; record resolver separately.
7. Empty queue, waiting state, validation errors, search/filtering, and sensible loading behavior. Resolved tickets remain in history; no time entry is required.
8. Administration mockup: technician list with active/inactive/setup-pending states and clearly simulated setup/recovery actions; no genuine links or secret credentials.

Use synthetic accounts sufficient to demonstrate an admin, a primary owner, a collaborator, and an unrelated technician. Include an unassigned ticket, assigned ticket, multi-device ticket, waiting ticket, and resolved ticket. Never copy names or student IDs from the real sheet. A demo state store is acceptable, with a clear reset function and documented non-persistence; it is not real access control. Keep domain types and mutation interfaces structured so M2/M3 can replace the demo store with Supabase without rewriting every view.

Suggested domain entities: app account, minimal requester, ticket, collaborator relation, device observation, note, activity event, optional work log. Keep primary owner separate from the collaborator list. Missing time is not zero. Do not implement future inventory, public intake, attachments, email, or timers in M1.
