# M2 — database and access enforcement

Local Supabase Postgres foundation for the Edison helpdesk: schema, row-level
security, transactional ticket operations, and an authenticated integration
suite. Everything here runs against a **local** stack only. No hosted project was
created or linked, nothing was deployed, and no real school record was imported.

The M1 demo interface is unchanged and still runs on its in-memory synthetic
store. Nothing in the UI talks to this database yet — porting it, real account
onboarding, and password recovery are M3.

## Setup and commands

Prerequisites: Docker running, and the project-local Supabase CLI
(`supabase@2.117.0`, a devDependency — no global install needed).

| Command | Purpose |
| --- | --- |
| `npm run db:start` | Start the local stack (Postgres 17, Auth, PostgREST, Studio) |
| `npm run db:status` | Show local URLs and keys |
| `npm run db:stop` | Stop the stack |
| `npm run db:reset:local` | Drop, recreate, and replay every migration locally |
| `npm run test:db` | Reset the local database, then run the integration suite |
| `npm run test:db:only` | Run the integration suite against the current local database |
| `npm run check` | Unchanged: typecheck, lint, unit tests, production build |

Local URLs: API `http://127.0.0.1:54321`, database `127.0.0.1:54322`, Studio
`http://127.0.0.1:54323`.

### Docker note for this machine

Docker Desktop's credential helper lives outside the default `PATH`, so image
pulls fail with `docker-credential-desktop: executable file not found`. The fix
used here is to prepend it for the session:

```bash
export PATH="/Applications/Docker.app/Contents/Resources/bin:$PATH"
```

The test harness adds that directory automatically when it shells out to the
CLI, so `npm run test:db` works without the export. A bare `npm run db:start`
in a fresh shell may need it.

### Local-only guards

Three independent guards make it impossible for these tests to touch a hosted
project:

1. `tests/db/support/local-only.ts` reads live connection details from
   `supabase status` and **refuses to run** unless the API host is loopback.
2. The same module refuses to run if `supabase/.temp/` contains a link marker
   (`project-ref`, `remote-db-url`, `pooler-url`), i.e. if the workspace has been
   linked to a hosted project.
3. `db:reset:local` passes the CLI's `--local` flag, which never targets a linked
   project.

The suite **fails rather than skips** when the database is unavailable. With the
stack stopped, `npm run test:db:only` exits 1 with:

```
Error: The local Supabase stack is not reachable (Command failed: npx --no-install supabase status -o json).
Start the local database first:
  npm run db:start
```

(Vitest also prints `No test files found` in that case, because global setup
throws before collection. The exit code is 1 and the cause is printed above it.)

### Credentials

No password, key, or token is committed. The local CLI keys are read at run time
from `supabase status`. Synthetic test users get a fresh random password on every
run (`Ed-${randomUUID()}`), held in memory only. Emails use the reserved
`edison.example` domain.

## Schema and TypeScript mapping

SQL is snake_case; the existing TypeScript types in `src/lib/domain/types.ts` are
unchanged. Mapping:

| Table | TypeScript | Notes |
| --- | --- | --- |
| `app_accounts` | `Account` | `id` **is** the `auth.users` id, so `auth.uid()` is the account id |
| `requesters` | `Requester` | Not login identities; minimal fields only |
| `tickets` | `Ticket` | Collaborators live in their own table, not an array |
| `ticket_collaborators` | `Ticket.collaboratorIds` | One row per participating technician |
| `device_observations` | `DeviceObservation` | Many per ticket |
| `notes` | `WorkNote` | |
| `work_logs` | `WorkLog` | Absent row = "not recorded" |
| `activity_events` | `ActivityEvent` | Append-only |

Column mapping is mechanical: `displayName` → `display_name`, `ownerId` →
`owner_id`, `resolvedById` → `resolved_by`, `createdAt` → `created_at`,
`submittedOn` → `submitted_on`, `requesterUnknown` → `requester_unknown`,
`identifiersNotApplicable` → `identifiers_not_applicable`, and so on.

Types and identity:

- `uuid` primary keys everywhere, generated by the database.
- Ticket numbers are generated by the database from `ticket_number_seq`
  (`EDT-1001`, `EDT-1002`, …). A client can never choose one.
- `timestamptz` for real event instants; `date` for school-local calendar dates
  (submission dates, work-log dates). `app_today()` returns the current
  **America/New_York** date, matching the M1 formatting rules — after 20:00 EDT
  the UTC date is already tomorrow, and using it would wrongly trip the
  "no future date" rules.

### Invariants enforced by the schema

CHECK constraints: title 1–120 characters after trimming; non-blank issue,
note body, waiting reason, cancel reason; valid channel/priority/status/role/
account-status/activity-kind; requester either known or explicitly unknown, never
neither; remote tickets carry no location; open tickets have no owner; assigned/
in-progress/waiting tickets have an owner and an assignment time; waiting
requires a reason and only waiting has one; a resolved ticket has a solution of
at least 5 trimmed characters plus a resolver and a resolution time; only a
resolved ticket has resolver fields, so **cancelling can never look like a
resolution**; work-log minutes are 1–1440, so a recorded zero is impossible and
"not recorded" stays distinguishable.

Triggers cover what a CHECK cannot (rules referencing the current time, and
cross-row rules): no future submission or work date; `created_at`, `created_by`,
`number` and `submitted_on` immutable after intake; the primary owner can never
also be a collaborator; `activity_events` reject UPDATE and DELETE from every
role, including the definer used by the RPCs.

Foreign keys to `app_accounts` are `ON DELETE RESTRICT`, so an account that
authored anything cannot be deleted and history cannot be cascaded away.
Deactivation, not deletion, is how someone leaves.

Indexes: partial index on the open queue (`priority, created_at` where unowned
and open), owner + status, status, submission date, resolved-at, collaborator by
account, and each child table by `ticket_id`.

## Trust boundaries

- **Identity comes only from `auth.uid()`.** No function accepts an actor id,
  role, author, or timestamp from the caller. The M1 browser store passes
  `actorId` and `now` into every operation; those parameters deliberately do not
  exist in the database contract.
- **Role and status come from `app_accounts`**, which no technician can write.
  Not from JWT metadata, not from a header.
- **Clients have SELECT only.** Supabase grants ALL on new public tables to
  `anon` and `authenticated` by default, so every table is explicitly revoked and
  then re-granted `SELECT` to `authenticated`. `anon` holds no table privilege
  and no EXECUTE on any function.
- **Every write goes through a SECURITY DEFINER RPC.** There are no INSERT,
  UPDATE, or DELETE policies at all, so even an accidental future grant has no
  policy to satisfy.
- **Helpers are hardened**: `SECURITY DEFINER`, `SET search_path = ''`, fully
  qualified references, minimal EXECUTE grants. They are definer-rights
  specifically so a policy on one table can consult another without re-entering
  that table's policy, which would recurse. Each returns only a boolean or the
  caller's own id, so none can be used as a data oracle. Internal helpers
  (`app_require_actor`, `app_lock_ticket`, `app_is_participant`, `app_log_event`,
  `app_require_contributor`) are revoked from every client role.
- **No views**, so there is no view that could bypass RLS.

## Permission contract

Row-level security governs reads; the RPCs govern writes. Both encode the same
matrix.

| Capability | Admin | Primary owner | Collaborator | Unrelated technician | Inactive / setup_pending / anon |
| --- | --- | --- | --- | --- | --- |
| Read ticket + child records | All | Own | Participating | Unowned open only | Nothing |
| Create ticket | Any channel, optional active owner | Walk-in, self-owned, today | Same | Same | No |
| Claim | Unowned open | Unowned open | Unowned open | Unowned open | No |
| Notes, devices, priority, waiting/resume | Active tickets | Active owned | Active participating | No | No |
| Resolve (solution required, time never) | Yes | Yes | Yes | No | No |
| Manage collaborators | Yes | Yes | No | No | No |
| Return unfinished work to Open Queue | Yes | Yes | No | No | No |
| Reassign to another owner, reopen, cancel | Yes | No | No | No | No |
| Log own time | Participating, non-cancelled | Owned, incl. resolved | Participating, incl. resolved | No | No |
| Account status administration | Yes (not own account) | No | No | No | No |

Two narrow lookups exist so technicians can work without a directory:

- `app_directory()` returns `id, display_name, role, status` for all accounts —
  enough to pick a collaborator and render "Dev Okafor added a work note". It
  deliberately excludes email, `created_at`, and the credential-action columns.
  Reading `app_accounts` directly still shows a technician only their own row.
- `requesters` is readable by any active account, so a technician can record a
  walk-in. This is a minimal requester lookup, documented separately from ticket
  visibility, and is **not** the future student/staff directory.
- `app_my_account()` returns the caller's own row only (`id, display_name, email,
  role, status`). It is available to inactive and setup_pending accounts on
  purpose: M3 needs it to route a restricted account to the right screen. It
  exposes no ticket information.

## RPC contract

All are `SECURITY DEFINER`, granted to `authenticated` only, and raise on failure
(so a failed call leaves no partial write). Each returns a `uuid` — the affected
ticket, note, device, or work log — and callers re-read through RLS, so a return
value can never leak a row the caller may not see.

| Function | Who | Effect |
| --- | --- | --- |
| `app_create_ticket(...)` | Active account | Intake. Admin: any channel, optional active owner, backdatable. Technician: walk-in, self-owned, today — anything else is rejected, not corrected. Creates the requester, collaborators, devices, and all events in one transaction |
| `app_claim_ticket(ticket)` | Active account | Unowned open ticket only. Sets owner, assignment time, status Assigned |
| `app_reassign_ticket(ticket, new_owner)` | Admin | Hand to another active technician |
| `app_return_ticket_to_queue(ticket)` | Owner or admin | Clears owner, assignment time, waiting state; sets Open. Keeps collaborators, notes, devices, logs, previous solution, history |
| `app_add_collaborator` / `app_remove_collaborator` | Owner or admin | Membership changes; removal revokes access but keeps authorship |
| `app_add_note(ticket, body)` | Participant or admin | Note + `note_added`; first contribution moves Assigned → In progress |
| `app_record_device(...)` | Participant or admin | Device observation; unknown serial/asset tag allowed |
| `app_set_priority(ticket, priority)` | Participant or admin | Logged change; no-op rejected |
| `app_set_waiting(ticket, reason)` / `app_resume_work(ticket)` | Participant or admin | Waiting requires a reason |
| `app_log_work(ticket, minutes, work_date, description)` | Participant or admin | Optional time, always attributed to the caller. Allowed after resolution, never on a cancelled ticket |
| `app_resolve_ticket(ticket, solution)` | Participant or admin | Requires ≥5 trimmed characters. Owner unchanged; resolver and time recorded separately |
| `app_reopen_ticket(ticket, reason)` | Admin | Clears resolver/time, keeps the previous solution as history |
| `app_cancel_ticket(ticket, reason)` | Admin | Never a resolution |
| `app_set_account_status(account, status)` | Admin | Active/inactive only, never own account or a setup-pending target. Password setup completion, role changes and account creation are not exposed |
| `app_my_account()` / `app_directory()` | See above | Lookups |

**Not implemented on purpose (M3):** creating auth users, issuing setup or
recovery links, and completing password setup. M2 exposes no function that would
make the M1 mockup's simulated credential actions look like real security
operations. The `last_credential_action_*` columns record only *that* an admin
acted, never a link or token.

## Transactions and locking

Every ticket mutation takes a shared transaction advisory lock before reading
its actor from `auth.uid()`, then locks the parent ticket, checks authorization
and state, and writes the change and history in the same transaction. Ordinary
ticket writes can run in parallel. Account-status changes take the matching
exclusive advisory lock **before** checking the admin or locking the target
account. This prevents stale account authorization while avoiding lock upgrades.

If a write starts first, deactivation waits for it to finish. If deactivation
starts first, the waiting write reads the new inactive status and fails. M3
trusted account/role changes must follow this same locking protocol; privileged
service-role maintenance is outside these client-RPC guarantees. Account-status
changes may briefly wait for unrelated writes; this is a deliberate simple
tradeoff for the small helpdesk workload.

This gives, proven by the concurrency tests:

- Two (and six) simultaneous claims → exactly one owner, exactly one `claimed`
  event; every loser gets the same generic message.
- Two simultaneous resolutions → exactly one `resolved` event, owner preserved.
- Resolve racing a return → exactly one coherent final state, never half-applied.
- A contribution racing a close or a collaborator removal → the write is either
  fully recorded or fully refused.
- Parallel intake → never a duplicate ticket number.

## Deliberate differences from the M1 demo

1. **A failed claim never names the owner.** The M1 demo said "EDT-1001 was
   already claimed by Sam Whitaker", which would turn the claim endpoint into an
   ownership oracle for any guessed ticket id. M2 returns one generic message —
   `That ticket is not available to claim.` — for missing, invisible,
   already-owned, and non-open tickets alike. Flagged in PROJECT_STATUS.md as the
   M2 privacy adjustment the handoff asked for; M3's UI must use this contract.
2. **Missing and invisible ids are indistinguishable** everywhere else too:
   `That ticket is not available to this account.`
3. **Technicians cannot backdate.** M1 left this as an open question and the UI
   simply dated walk-ins today; the database now rejects a backdated technician
   walk-in outright.
4. **Zero-minute work logs are rejected** rather than stored, so "not recorded"
   is unambiguous.

## Test results

`npm run test:db` — resets the local database, replays all eight migrations, then
runs the suite against the live stack. **118 tests in 9 files, all passing after Codex review.**

| File | Tests | Covers |
| --- | --- | --- |
| `tests/db/schema.test.ts` | 21 | Fresh migration apply; constraints reject invalid state; immutability; append-only history; account deletion blocked by history |
| `tests/db/visibility.test.ts` | 20 | Queue/owned/collaborating/closed visibility; child-table inheritance; anonymous, inactive and setup_pending see nothing; directory and self-status field lists; public signup refused |
| `tests/db/privilege.test.ts` | 15 | Direct INSERT/UPDATE/DELETE refused on every table; no self-elevation; authorship and timestamps server-side; missing vs invisible parity; claim never names an owner |
| `tests/db/intake.test.ts` | 15 | Admin defaults and backdating with real creation time preserved; technician walk-in/self-owned/today with forged fields rejected; failed intake rolls back completely |
| `tests/db/lifecycle.test.ts` | 22 | Claim; owner and collaborator resolution with no time; blank/trivial solution refused; reopen then re-resolve retaining history; return-to-queue preserving everything, reclaim, and former-owner access loss |
| `tests/db/revocation.test.ts` | 5 | Deactivation and collaborator removal revoking access on an already-open session, history intact, admin retains visibility for reassignment |
| `tests/db/concurrency.test.ts` | 8 | Real competing calls over separate sessions: claims, resolutions, resolve vs return, contribution vs close/removal, parallel intake, deactivation vs contribution |

| `tests/db/unowned-authorization.test.ts` | 9 | NULL-safe denial of unclaimed contributions and collaborator management; invisible unowned closed-ticket RPC denial; retained collaborator authority and reclaim |
| `tests/db/actor-locking.test.ts` | 3 | Deterministic lock barriers for both deactivation/write orderings; no setup bypass through status RPC |

The original 106 tests passed before review, but eight of the nine initial
unowned-ticket regressions failed against that implementation. Migrations 006
and 007 fix the permission and account-authorization gaps. The final suite above
was run after replaying all migrations from a fresh local database.

All authorization assertions run through real signed-in sessions over PostgREST.
The service role is used only to seed identities and to read ground truth, never
to perform an operation whose authorization is under test.

`npm run check` remains green: typecheck, lint, **80 unit tests in 7 files**, and
a successful production build. Database tests are excluded from it by config.

## Gaps and follow-ups

1. **The UI is still demo-backed.** No screen reads or writes this database. M3
   replaces `src/lib/demo/store.tsx` with real calls and wires Supabase Auth.
2. **No account onboarding.** Creating accounts and issuing setup/recovery links
   is M3. Today an account exists only if a privileged operator inserts it, which
   is what the test harness does.
3. **Preserved approved behavior:** a return to the Open Queue preserves collaborators,
   and a collaborator can still resolve the now-unowned ticket, producing a
   resolved ticket with no primary owner. This matches the M1 rules (a
   participant may resolve; an unowned ticket may be resolved), and the
   concurrency test asserts it as one of two coherent outcomes. Codex retained this behavior because returning work explicitly preserves collaborators. Unrelated technicians must claim before contributing.
4. **No `seed.sql`.** Seed data would need app accounts, which need auth users,
   which would mean committing a password. Identities are created ephemerally by
   the harness instead. A reviewer wanting to browse data in Studio should run
   `npm run test:db`, which leaves a populated local database behind.
5. **Not tested here:** backup and restore, performance at volume, and anything
   hosted. Those belong to M4.
6. **`supabase status` keys are the CLI's standard local development keys.** They
   are identical on every local install and are not secrets, but they are still
   read at run time rather than written to any file.
